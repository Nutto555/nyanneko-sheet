<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client env var -> Auth check | VITE_ADMIN_PASSWORD exposed in client bundle; simple gate, not real security |
| Admin input -> Supabase | Strategy/template form data flows from admin UI to Supabase via Zod-validated service layer |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Spoofing | useAdminAuth password comparison | accept | Password is a simple client-side gate per design decision. Not real auth. VITE_ADMIN_PASSWORD is in the client bundle. This is acceptable for a single-guild tool where the goal is preventing accidental edits, not blocking determined attackers. Real auth deferred to v2 (AUTH-01). |
| T-05-02 | Tampering | sessionStorage admin flag | accept | A user could set sessionStorage manually to bypass the gate. Acceptable per design decision -- this is a convenience gate, not a security boundary. RLS policies on Supabase tables are the real write protection. |
| T-05-03 | Tampering | Strategy/template mutation inputs | mitigate | All mutations flow through Zod schemas in strategies.ts (createTemplateSchema, updateStrategySchema, etc.) which validate input shape and types before any Supabase write. |
</threat_model>
