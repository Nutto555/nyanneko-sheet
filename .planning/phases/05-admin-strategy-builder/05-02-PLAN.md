<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin UI -> Supabase | Strategy form data (notes, conditions) flows from admin input to DB |
| Client -> dnd-kit | Drag events produce reordered IDs sent to Supabase |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04 | Tampering | StrategyForm input data | mitigate | All form submissions flow through Zod schemas (createStrategySchema, addConditionsSchema) in the service layer before reaching Supabase. Character IDs are validated as UUIDs. Free text fields (strategy_notes, condition_note) are rendered via JSX interpolation (React escapes). |
| T-05-05 | Tampering | Drag reorder producing invalid IDs | mitigate | reorderStrategies() accepts only string IDs and updates matching rows per template_id. Non-matching IDs produce no-op updates. The service uses .eq('template_id', templateId) scoping so one template's reorder cannot affect another. |
| T-05-06 | Elevation of Privilege | Admin page accessible without auth | mitigate | AdminAuthGate wrapper prevents rendering of admin UI until password is provided. Supabase RLS policies on write operations provide server-side enforcement independent of client-side gate. |
</threat_model>
